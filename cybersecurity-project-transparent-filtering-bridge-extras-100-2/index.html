The Context

For the first half of the year, things were stable with the older version of the setup file I had created for the wpa_supplicant, which controls the WiFi interface I use to manage OPNSense on the miniPC it runs off of.

OPNSense versions 26.1+ provided no real issues aside from the need to reapply the script whenever an update occurred, because the update would revert the wpa_supplicant file back to its old state.

OPNSense announced a planned upgrade to version 26.7 on July 15, 2026, at which time support for 26.1+ would cease. I waited a few days, checked the r/OPNSense thread on the update, saw that N100 miniPCs like mine had few issues, and proceeded with the update.

The First Problem

After the minor hassle of updating to 26.1.11 to get to update to 26.7, the first real indication of a problem was when I tried to get into the shell to look at wpa_supplicant, and this happened:

The above screenshot is a small segment of the fast moving stream of text that would fill the screen before the miniPC crashed.

What was interesting about this crash was OPNSense would boot properly, allow me to enter the shell, and then crash after about 1-2 minutes from boot completion.

I explored several avenues to dealing with this, including reinstalling OPNSense. I couldn't get the installer to work, so I was left with using an option I had never used before: Reset to Default Configuration.

Since I had a backup of the configuration made before the update, I saw little risk in using this option. And it worked.

The Second Problem

The fact that resetting to default configuration solved the problem at all indicated that it was at least partially due to configuration settings, which promised headaches in the future.

However, the new problem was that I would have to figure what to do with the wpa_supplicant, because resetting to default hadn't enabled it to connect to my home network.

Unfortunately, I managed to botch taking a picture of the actual code for the default wpa_supplicant implementation, so I don't have that as a reference. Even more annoying, the source code is not easily discoverable online, so I was not able to reference that instead.

Attempting to use the old script didn't work, so I was left an option I very much did not like: using ChatGPT to generate diagnostic scripts.

If you've read previous posts in this series, you might be wondering why I would say that. And the answer is very simple: since the start of 2026, the functionality of the free ChatGPT account has steadily degraded (aka enshittification). As of July 2026, if you upload too many documents, you get a cooldown before you can upload more. If you want it to do code, it can't be too big, or it won't show up in the chat window and it can't be compiled into a file you can download. If you use too many token, you get a cooldown on the default model and forced to use a worse model or wait. And so.

## Conclusion

The log does **not** indicate a hardware, firmware, or Intel `iwlwifi` driver failure. The Wi-Fi adapter initializes successfully, the correct firmware loads, and the wireless interface is created.

The failure occurs because the system later attempts to create `wlan0` a second time, causing `wpa_supplicant` initialization to fail before any scan, association, or DHCP activity can occur. The evidence points most strongly to duplicate WLAN interface creation or conflicting network initialization logic, likely involving OPNsense's network configuration rather than the wireless driver itself.

## Conclusion

This is **not**:

* an Intel `iwlwifi` driver bug
* a firmware problem
* a LinuxKPI issue
* a hardware failure
* a WPA configuration syntax error

The failure is caused by **conflicting `wpa_supplicant` configuration sources**, which result in the interface being managed under two different names.

## Root cause (≈99% confidence)

There is a direct configuration conflict between **`/etc/rc.conf`** and **`/etc/rc.conf.local`**.

`/etc/rc.conf` specifies:

```text
wpa_supplicant_iface="iwlwifi0_wlan0"
```

while `/etc/rc.conf.local` specifies:

```text
wpa_supplicant_iface="wlan0"
```

The diagnostic also shows that `sysrc` resolves the active value as:

```text
wpa_supplicant_iface: wlan0
```

even though `/etc/rc.conf` contains `iwlwifi0_wlan0`. 

This means the later-loaded configuration is overriding the earlier one.

---

## The boot sequence explains the failure

The kernel initializes normally:

* detects the Intel AX101
* loads firmware
* creates `wlan0`
* renames it to `iwlwifi0_wlan0`

Immediately afterward:

```
ifconfig: interface wlan0 already exists
/etc/rc.d/wpa_supplicant: ERROR: Failed to create wlan0
```

appears in the boot log. 

This indicates that the `rc.d/wpa_supplicant` script still believes the interface should be named `wlan0` and attempts to create it again.

---

## Why `wpa_supplicant` never starts

The Stage 2 diagnostics show:

* no `wpa_supplicant` process
* `pgrep` returns nothing
* `sockstat` contains no `wpa_supplicant`
* `/var/run/wpa_supplicant` contains only an empty directory with no control socket  

Therefore the daemon never successfully starts.

Without `wpa_supplicant`:

* no authentication
* no association
* no WPA handshake

---

## The wireless driver is healthy

The driver:

* detects the Intel AX101
* uploads firmware successfully
* exposes the wireless interface
* reports the parent interface correctly

The interface exists as:

```
iwlwifi0_wlan0
```

and is operational from the driver's perspective. 

Nothing in the diagnostics suggests a driver fault.

---

## The WPA configuration is valid

The generated configuration file contains:

* `ctrl_interface`
* `network`
* `ssid`
* `psk`
* `key_mgmt=WPA-PSK`

and is syntactically correct. 

The configuration is simply never consumed because the daemon fails before startup.

---

## Secondary finding

The diagnostics reveal another inconsistency:

```
/etc/rc.conf
    wpa_supplicant_iface="iwlwifi0_wlan0"

/etc/rc.conf.local
    wpa_supplicant_iface="wlan0"
```

At the same time, both files reference the same configuration file:

```
/var/etc/wpa_supplicant_iwlwifi0_wlan0.conf
```

This mixed configuration strongly suggests an incomplete migration from the traditional `wlan0` naming convention to `iwlwifi0_wlan0`. 

---

## What is **not** the problem

The Stage 2 logs rule out:

* Firmware loading failure
* Unsupported Intel AX101 hardware
* Missing firmware files
* Invalid WPA-PSK configuration
* Missing `if_iwlwifi` kernel module
* Missing `wpa_supplicant` package

---

## Most likely origin

This appears to be a **configuration generation issue**, not a runtime issue.

Possible sources include:

* OPNsense generating inconsistent `rc.conf.local`
* a stale configuration remaining after switching to the `iwlwifi` driver
* conflicting interface naming logic between OPNsense and the FreeBSD `rc.d/wpa_supplicant` script

The conflict is visible in the configuration files themselves before any network traffic occurs.

## Confidence assessment

| Finding                                                                     | Confidence |
| --------------------------------------------------------------------------- | ---------: |
| Conflicting `wpa_supplicant_iface` values (`wlan0` vs `iwlwifi0_wlan0`)     |        99% |
| `wpa_supplicant` exits before starting                                      |        99% |
| Duplicate interface creation is a consequence of the configuration conflict |        98% |
| Intel `iwlwifi` driver defect                                               |        <1% |
| Firmware defect                                                             |        <1% |
| Hardware failure                                                            |        <1% |

From these diagnostics, the most likely corrective action is to eliminate the conflicting interface-name definitions so that **all** `wpa_supplicant` configuration sources reference the same interface name. Once the interface naming is consistent, `rc.d/wpa_supplicant` should no longer attempt to recreate `wlan0`, allowing the daemon to start and proceed with WPA association.

Based on the script and the errors, the problem is **not `wpa_supplicant` itself**. The script assumes the FreeBSD 14.x Intel wireless model, but **FreeBSD 15.1 changed parts of the `iwlwifi`/802.11 initialization sequence**.

The sequence of failures is significant:

```
ifconfig: SIOCIFCREATE2 (iwlwifi0_wlan0): Invalid argument
        ↓
wlan interface never created
        ↓
wpa_supplicant cannot bind to interface
        ↓
wpa_supplicant not running
```

The first failure is therefore the root cause.

## Problems in the current script

### 1. Incorrect interface creation

The script currently does

```sh
ifconfig "${wpa_supplicant_parent}" create \
    wlandev "${wpa_supplicant_parent}"
```

For Intel this expands to

```sh
ifconfig iwlwifi0 create wlandev iwlwifi0
```

This is **no longer reliable** on newer kernels.

The supported form is

```sh
ifconfig wlan create wlandev iwlwifi0 name iwlwifi0_wlan0
```

or

```sh
ifconfig wlan0 create wlandev iwlwifi0
```

depending on configuration.

Using the parent interface as the object being created now returns

```
SIOCIFCREATE2
Invalid argument
```

---

### 2. Script ignores rc.conf

FreeBSD 15 expects the networking framework to own cloned interfaces.

Instead of manually creating

```
iwlwifi0_wlan0
```

the preferred configuration is

```sh
wlans_iwlwifi0="wlan0"
```

or

```sh
wlans_iwlwifi0="iwlwifi0_wlan0"
```

Then

```
service netif start
```

creates it.

The rc.d script should **verify** the interface exists.

It should **not** normally create it itself.

---

### 3. Wrong REQUIRE dependency

Current:

```sh
REQUIRE: NETWORKING
```

`NETWORKING` completes before cloned wlan interfaces exist.

Instead use

```sh
REQUIRE: netif
AFTER: devd
```

or simply

```
REQUIRE: LOGIN netif
```

depending on when you want it.

Otherwise

```
service wpa_supplicant start
```

runs before wlan creation.

---

### 4. Missing parent validation

Before doing anything the script should verify

```sh
ifconfig -l
```

contains

```
iwlwifi0
```

If not

```
kldload if_iwlwifi
```

is insufficient.

It also needs

```
kldload firmware
```

(or the proper Intel firmware module)

and wait for the device.

---

### 5. Race condition

Immediately after loading

```
if_iwlwifi
```

the firmware loads asynchronously.

The script immediately executes

```
ifconfig wlan create
```

before firmware initialization finishes.

The result is

```
Invalid argument
```

A retry loop is much safer:

```sh
i=0

while [ $i -lt 20 ]
do
    if ifconfig iwlwifi0 >/dev/null 2>&1
    then
        break
    fi

    sleep 1
    i=$((i+1))
done
```

---

### 6. Wrong configuration filename

The script defines

```sh
wpa_supplicant_conf="/var/etc/wpa_supplicant_wlan0.conf"
```

but generated

```
/var/etc/wpa_supplicant_iwlwifi0_wlan0.conf
```

These do **not** match.

So even if the interface existed,

```
wpa_supplicant
```

would fail because the configuration file does not exist.

---

### 7. No interface existence check

Before starting

```
wpa_supplicant
```

the script should verify

```sh
ifconfig "${iface}"
```

returns success.

If not

```
err 1 "${iface} does not exist"
```

instead of attempting to launch.

---

### 8. Missing carrier wait

Even after the interface exists,

```
802.11
```

is not immediately ready.

Wait until

```
ifconfig wlan0
```

reports

```
status: no carrier
```

or

```
status: associated
```

before launching `wpa_supplicant`.

---

## Recommended FreeBSD 15.1 startup order

The service should follow this sequence:

```
Load firmware
        ↓
Load if_iwlwifi
        ↓
Wait for iwlwifi0
        ↓
Verify parent exists
        ↓
Verify wlan clone exists
        ↓
Create clone only if missing
        ↓
Bring interface down
        ↓
Bring interface up
        ↓
Wait for 802.11 initialization
        ↓
Launch wpa_supplicant
        ↓
Verify PID
        ↓
Run DHCP
```

---

## The biggest architectural change I recommend

Instead of having the script create interfaces itself:

```
ifconfig create ...
```

delegate interface creation to FreeBSD networking.

Your setup script should generate:

```sh
wlans_iwlwifi0="iwlwifi0_wlan0"

ifconfig_iwlwifi0_wlan0="WPA DHCP"

create_args_iwlwifi0_wlan0="country US"

wpa_supplicant_enable="YES"

wpa_supplicant_conf_file="/var/etc/wpa_supplicant_iwlwifi0_wlan0.conf"
```

Then startup becomes simply

```
service netif restart
service routing restart
```

This uses the networking framework exactly as intended in FreeBSD 15.1, rather than duplicating interface creation logic in a custom rc.d script.

## Additional issues in the uploaded script

I also found these bugs:

* `wpa_supplicant_conf` points to the wrong filename.
* `status_cmd` only checks the PID file and does not verify the process is running.
* `stop_cmd` does not wait for process termination before removing the PID file.
* No retry logic if firmware initialization is delayed.
* No verification that `/var/run/wpa_supplicant` exists before launching.
* No automatic DHCP (`dhclient`) after successful association.
* No logging via `logger` or `syslog`, making failures harder to diagnose.

Given the FreeBSD 15.1 networking changes, I would recommend replacing most of the custom rc.d service logic rather than patching it. A redesigned version that relies on the native `netif` framework, handles Intel firmware initialization, performs robust validation and retry logic, and includes detailed logging will be substantially more reliable than adapting the current script.

Configuring OPNSense 26.7

Having anticipated trouble, I downloaded a backup XML version of my OPNSense configuration before initiating the update to 26.7. However, the crashing I saw after doing the update went away after I reset to the default configuration. This meant that the safest course of action was to do a partial setup of the transparent filtering bridge, export an updated OPNSense config XML file, then splice data from the old file into the new file, and then upload that into OPNsense.

Not helping this process were two semi-related problems:

  • OPNSense firewall was in effect on the WiFi interface, forcing me to disable the firewall to access the WebGUI.
  • The WebGUI's performance was pretty terrible.

What would happen is that as I configured settings, saving and applying those settings caused the firewall to restart, forcing me to physically go to the miniPC and type in the command to disable the firewall. A combination of firewall rules and applying a hotfix update eventually improved WebGUI access and performance/loading.

Eventually, I reached a point where I felt comfortable in downloading the then-current configuration and integrating the old data into it. When I did, I discovered that the layouts of the two configuration files greatly differed:

The completely different layout of the new configuration XML, when combined with the changes to the WiFi stack, probably contributed to why OPNSense kept crashing when I first upgraded.

What I discovered, to my annoyance, was that the import process didn't work for rules - and looking on the OPNSense GitHub Issues page, this seems to be an issue with 26.7, not my work. So I was left with 50+ blank rule files that I had to manually configure anyway.

Initially, it also didn't work for Aliases either. However, I made a dummy alias (imaginatively named "Dummy"), then exported the configuration file, replaced the dummy alias with the aliases from the old config, and that properly imported. After doing that, I added a new set of IP block lists to my list of aliases to increase coverage.

Rebuilding my rules took a while, as I chose to implement separate IN/OUT rules with each alias for finer control and logging. This resulted in 56 blocking rules, 2 diagnostic rules for gathering data on connectivity to my ISP's infrastructure, and 2 fallback rules allowing traffic in and out of the bridge. The fallback rules are placed last in the list, executing after all the other rules, to ensure malicious and ad traffic are blocked.

After many long hours of work configuring the device, it was finally time to connect it to the modem and router. And that's when I discovered a new problem.

How Spectrum Handles DHCP

Like many Floridians, my internet access is handled by Spectrum, the Charter owned ISP. You can easily find many reports of dissatisfaction with Spectrum on a wide variety of issues, but this one is a pretty obscure one. That's because most consumers don't put a transparent filtering bridge/firewall between their modem and router.

What I discovered is that Spectrum's DHCP process triggers one of the alias/block list based block rules, preventing the router from receiving an IP address:

OPT2 In [DATE] UDP 0.0.0.0:68 255.255.255.255:67 block Block Firehol_level1 coming IN

Looking at the Virus Total page reveals why someone would put 0.0.0.0 on a block list:

This forced me to implement an in/out pass rule, but I minimized the window of vulnerability with OPNSense's scheduling feature. This allowed me to set a scheduled time for the rule to activate, and the tightest time window possible (15 minutes) was more than sufficient for the DHCP lease/renewal process to complete. (It turns out this is a major issue with the firewall scheduler and requires rebuilding the system.)

Since the DHCP lease seems to hold until either the router restarts or something happens to the network connection on Spectrum's end, this rule only needs to work once a week after I managed to get the rule functional.

Suricata Configuration

This is where things became interesting, because it turns out Suricata is connected to the crashing I was seeing when I began the 26.7 upgrade.

The precise mechanics of this crash are not clear to me, because they only occurred partway through the configuration process. As far as I can tell, it was not the act of enabling Suricata, but something related to either the way it processes packets and/or the data sources it uses that triggered the crash.

This forced me to once again reset OPNSense to default settings, but I had made a backup of the most recent configuration, minus a few additions, that allowed me to quickly restore functionality.

This issue was reported on GitHub.

Future Upgrade Planning

I went into this upgrade process thinking I had a solid plan. If anything bad happened, I could just reload the backed up config file, or at worst, extract data from the old file, splice it into a new file, and upload that into OPNSense. Events proved me completely wrong on that assessment.

The easy part of a better, more comprehensive upgrade plan is all on the OPNsense end:

  • Make a backup of the configuration before upgrading.
  • Make a CSV export of the alias list before upgrading.
  • Make a CSV export of the firewall rule list before upgrading.

This plan would allow me to bypass any and all configuration related issues, albeit at the cost of forcing me to manually rebuild my Suricata config each and every time I couldn't roll it over/import it.

The much harder part of the new upgrade plan is figuring out what to do to prepare a virtual machine environment for OPNSense for testing purposes. For the simple purpose of examining the code for the wpa_supplicant, any virtual machine will do. However, specifically testing out the scripts I've made might be impossible, depending on whether or not I can emulate the devices in the miniPC. Further research is necessary.

Next Steps

After four days wrestling with these problems, I am more than happy to take a step back and monitor the transparent filtering bridge to see if it can operate normally, or there's some other problems that I haven't yet experienced.

Takeaways

  • I used a custom wpa_supplicant setup file for managing OPNSense on a miniPC via WiFi.
  • OPNSense versions 26.1+ were stable, but updates required reapplying the script because they reverted the wpa_supplicant file.
  • I updated to OPNSense 26.7 after confirming minimal issues for N100 miniPCs on Reddit.
  • After updating to 26.7, the miniPC crashed 1-2 minutes after booting when attempting to access the shell.
  • Reinstalling OPNSense failed, so I used “Reset to Default Configuration,” which resolved the crashing.
  • A configuration backup existed prior to the update, reducing the risk of this approach.
  • Resetting to default configuration fixed the crash but left the wpa_supplicant not connected to the home network.
  • The old script failed, leading me to use ChatGPT for diagnostic scripts despite concerns about ChatGPT’s declining functionality (“enshittification”).
  • ChatGPT generated a diagnostic script that identified the issue as duplicate WLAN interface creation or conflicting network initialization logic, not hardware or driver failure.
  • Further diagnostics revealed conflicting interface names (wlan0 vs. iwlwifi0_wlan0) prevented wpa_supplicant from starting.
  • ChatGPT analyzed the original script and identified several bugs, recommending a redesign rather than patching.
  • Due to ChatGPT’s limitations in generating full scripts, I requested a “caveman mode prompt” for Qwen 3.6.
  • I used a local Qwen 3.6 fine-tune for coding, but it failed to produce a functional script despite multiple iterations.
  • I switched to OpenCode due to context window limitations and exhaustion with Qwen 3.6.
  • Various models (North Mini Code Free, Nemotron 3 Ultra Free, MiMo V2.5) were used, with varying success and significant context window issues.
  • It took 16 conversation sessions to achieve a minimum viable script.
  • I performed a partial setup, exported the config, and spliced old data into the new XML file.
  • The new configuration XML layout differed significantly from the old one, likely contributing to the initial crashes.
  • Firewall rules and aliases did not import correctly, requiring manual reconfiguration.
  • Spectrum’s DHCP process triggered a block rule for 0.0.0.0, preventing the router from getting an IP.

  • Enabling Suricata or its packet processing/data sources likely caused the initial crashes.
  • I had to reset OPNSense to default settings again but could quickly restore from a recent backup.
  • A better plan includes backing up the configuration, alias list, and firewall rule list as CSVs before upgrading.
  • Testing in a virtual machine is considered but may be limited by hardware emulation constraints.
  • I will monitor the transparent filtering bridge for stability and any new issues.
